## Stage 5: 报告生成引擎

### 核心技术栈

| 组件 | 技术选型 | 理由 |
|-----|---------|------|
| PDF 生成 | **WeasyPrint** | HTML/CSS 转 PDF，支持中文，布局灵活 |
| HTML 模板 | **Jinja2** | Python 原生，项目已使用 |
| 静态图表 | **Matplotlib** | 成熟稳定，适合静态报告 |
| 交互图表 | **Plotly** | HTML 报告的交互式图表 |
| 异步任务 | **Celery** | 项目已使用，专用队列隔离 |

### 架构决策

#### 1. 为什么选择 WeasyPrint？

**对比其他方案**：

| 方案 | 优势 | 劣势 | 结论 |
|-----|------|------|------|
| **WeasyPrint** | HTML/CSS 熟悉、中文支持好 | 需要系统依赖 | ✅ 推荐 |
| ReportLab | 纯 Python、无依赖 | 布局编码复杂 | ❌ 不推荐 |
| wkhtmltopdf | 功能强大 | Qt依赖重、已停止维护 | ❌ 不推荐 |
| Playwright PDF | 渲染准确 | 资源占用大 | ⚠️ 备选 |

**最终选择**: WeasyPrint
- 理由：平衡了易用性和功能性
- 系统依赖：`libpango`, `libcairo`（可接受）

#### 2. 队列隔离策略

```python
CELERY_TASK_ROUTES = {
    'detection': '检测任务',     # 高优先级，快速处理
    'reports': '报告生成',       # 中等优先级，可延迟
    'training': '模型训练'       # 低优先级，长时间运行
}
```

**隔离原因**：
- 报告生成耗时长（30-60秒）
- 避免阻塞实时检测任务
- 便于资源分配和监控

#### 3. 数据聚合优化

**问题**：大数据量聚合查询慢
**解决方案**：
1. 数据库索引：`user_id`, `created_at`
2. 分页查询：限制单次查询数据量
3. 缓存（未来）：预聚合关键指标

### 关键挑战

| 挑战 | 解决方案 |
|-----|---------|
| PDF 中文字体 | 在 HTML 中指定中文字体族 |
| 图片路径问题 | 使用 base64 编码嵌入或绝对路径 |
| 内存占用 | 及时清理临时图表文件 |
| 大数据量 | 分页查询 + 限制时间范围 |

## Stage 6: 数据标注工具

### 核心技术栈

| 组件 | 技术选型 | 理由 |
|-----|---------|------|
| 标注界面 | **Konva.js + Vue** | Canvas 性能好，Vue 集成简单 |
| 备选方案 | Label Studio Frontend | 功能完整但较重，可作为未来升级选项 |
| 数据格式 | YOLO / COCO | 业界标准，YOLO 训练兼容 |

### 架构决策

#### 1. 标注库选型对比

| 方案 | 功能性 | 易用性 | 集成难度 | 性能 | 决策 |
|-----|-------|--------|---------|------|------|
| **自研 (Konva.js)** | ⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ✅ 推荐 |
| Label Studio | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐ | ⭐⭐⭐ | ⚠️ 备选 |
| react-image-annotate | ⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐⭐ | ⚠️ 备选 |
| Annotorious | ⭐⭐⭐⭐ | ⭐⭐ | ⭐⭐ | ⭐⭐⭐ | ❌ 不推荐 |

**最终选择**: Konva.js 自研轻量级标注工具
- 理由：
  - 项目需求简单（只需边界框标注）
  - 完全可控、易于定制
  - 性能优秀（Canvas 渲染）
  - 与 Vue 3 集成良好

**未来升级路径**：
- 如果需要更复杂的标注类型（分割、关键点），可考虑集成 Label Studio

#### 2. 数据优先级策略

```
获取标注数据流程：
1. 优先查询 annotations 表
2. 如果存在 → 返回人工标注（is_corrected = true）
3. 如果不存在 → 返回原始检测结果
```

**好处**：
- 保证标注数据权威性
- 向后兼容（未标注时显示检测结果）
- 支持渐进式标注

#### 3. 导出格式支持

**YOLO 格式**：
```
<class_id> <x_center> <y_center> <width> <height>
```
- 坐标归一化到 [0, 1]
- 每个图像一个 `.txt` 文件
- 使用场景：YOLO 模型训练

**COCO 格式**：
```json
{
  "images": [...],
  "annotations": [...],
  "categories": [...]
}
```
- 单个 JSON 文件
- 使用场景：模型评估、数据集共享

### 关键挑战

| 挑战 | 解决方案 |
|-----|---------|
| 前端性能 | 使用 Canvas 而非 SVG/DOM |
| 大图像 | 图像压缩 + 虚拟化渲染 |
| 数据一致性 | 明确优先级：标注 > 检测 |
| 开发工作量 | 只实现核心功能，渐进增强 |

## Stage 7: 模型训练系统

### 核心技术栈

| 组件 | 技术选型 | 理由 |
|-----|---------|------|
| 训练框架 | **Ultralytics YOLO** | 项目已使用，API 友好 |
| GPU Worker | **Celery + solo pool** | 避免 GPU 多进程冲突 |
| 日志收集 | **stdout 重定向** | 捕获 YOLO 训练输出 |
| 数据准备 | **自研脚本** | 从标注数据生成 YOLO 格式 |

### 架构决策

#### 1. GPU Worker 配置

**关键决策**：使用 `solo` pool 而非默认的 `prefork`

```bash
celery -A app.core.celery_app worker \
  -Q training \
  --pool=solo \        # ⭐ 关键
  --concurrency=1
```

**原因**：
- GPU 不支持多进程共享
- YOLO 训练本身已使用多线程
- 避免 CUDA 初始化冲突
- 简化资源管理

#### 2. 队列严格隔离

```
┌──────────────┐
│ API 请求     │
└──────┬───────┘
       │
       ▼
┌──────────────────────────────┐
│   Celery 任务路由             │
├──────────────────────────────┤
│ detection  → Worker 1 (CPU)  │
│ reports    → Worker 2 (CPU)  │
│ training   → Worker 3 (GPU)  │ ⭐
└──────────────────────────────┘
```

**隔离必要性**：
- 训练任务可能运行数小时
- 避免阻塞实时检测任务
- GPU 资源独占
- 便于监控和故障隔离

#### 3. 数据准备流程

**最难的部分**：标注数据 → YOLO 格式

```python
标注数据 (JSON):
{
  "annotations": [
    {"class": "fish", "bbox": [100, 200, 300, 400], ...}
  ]
}

↓ 转换脚本

YOLO 格式:
images/
  train/
    img1.jpg
  val/
    img2.jpg
labels/
  train/
    img1.txt  # 0 0.5 0.5 0.2 0.3
  val/
    img2.txt
data.yaml  # 配置文件
```

**关键步骤**：
1. 从数据库获取标注数据
2. 复制原始图像到训练目录
3. 转换边界框格式（绝对坐标 → 归一化）
4. 生成 YOLO 标注文件（.txt）
5. 生成 data.yaml 配置

**易错点**：
- 坐标归一化计算错误
- 图像路径问题
- 类别 ID 映射错误
- 数据集划分比例

#### 4. 日志收集方案

**问题**：YOLO 训练输出到 stdout，难以捕获

**解决方案**：
```python
import sys

# 重定向 stdout
sys.stdout = open(log_file, 'a')
sys.stderr = open(log_file, 'a')

# 执行训练
model.train(...)

# 恢复 stdout
sys.stdout = sys.__stdout__
sys.stderr = sys.__stderr__
```

**实时日志查看**：
- 后端：使用 StreamingResponse 流式传输日志文件
- 前端：WebSocket 或轮询更新

#### 5. 模型注册流程

```
训练完成
  ↓
找到 best.pt
  ↓
复制到 /models 目录
  ↓
在 ml_models 表创建记录
  ↓
关联到 training_jobs
  ↓
用户可选择使用新模型
```

### 关键挑战

| 挑战 | 解决方案 | 优先级 |
|-----|---------|--------|
| GPU 资源管理 | 专用 Worker + solo pool | 🔴 高 |
| 数据准备脚本 | 充分测试 + 详细日志 | 🔴 高 |
| 训练时间长 | 异步任务 + 进度跟踪 | 🟡 中 |
| 日志收集 | stdout 重定向 | 🟡 中 |
| 队列隔离 | 独立 Worker 和队列 | 🔴 高 |
| 模型版本管理 | 数据库记录 + 文件命名 | 🟢 低 |

## 总结

### 技术可行性评估

| Stage | 技术成熟度 | 开发难度 | 风险等级 | 建议 |

4. **渐进开发**：MVP 优先，避免过度设计
5. **充分测试**：特别是 Stage 6 和 Stage 7
