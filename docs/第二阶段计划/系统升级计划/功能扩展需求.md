这是一个绝佳的计划！系统上线只是第一步，真正的价值来自于持续的迭代和深化。您已经构建了一个“检测工具”，现在我们要把它升级为一个“智能分析平台”和“数据增值系统”。

这里是您提到的三个层次功能的**详细展开规划**，包含每个功能的核心价值、页面设计、后端架构和关键挑战。

------



### 层次一：深化核心体验（增强现有功能）





#### 1. 📈 用户仪表盘 (User Dashboard)



- 🎯 核心价值：

  改变用户登录后的“无目的”状态。从一个被动的工具（/detect）转变为一个主动的“信息中心”（/dashboard），让用户在 10 秒内了解“我的现状”。

- **🎨 页面设计与 UX 流程 ( `/dashboard` )：**

  1. **布局：** 采用 2x2 或 2+2 的卡片式网格布局。
  2. **卡片 1：关键指标 (Stats Cards)**
     - 一行 4 个小卡片：`总检测次数`、`本周处理视频 (个)`、`总检测目标 (个)`、`最常检测到的目标`。
  3. **卡片 2：快速入口 (Quick Actions)**
     - 两个醒目的按钮：`[ 🖼️ 开始新的图片检测 ]` 和 `[ 🎥 上传视频任务 ]`。
  4. **卡片 3：近期活动 (Recent Activity)**
     - 一个可滚动的列表，显示“最近 5 条检测历史”及其状态（`处理中...`, `✓ 已完成`）。
     - 提供一个 `[ 查看全部 ]` 的链接，跳转到 `/history` 页面。
  5. **卡片 4：模型使用偏好 (Model Usage)**
     - 一个简单的环形图 (Donut Chart)，显示用户最常使用的 YOLO 模型（例如：60% V8n, 40% V5s）。

- **⚙️ 后端架构与 API：**

  - **新 API：** `GET /api/v1/dashboard/stats`
  - **后端逻辑：**
    1. 此 API 需认证，并获取 `current_user.id`。
    2. **数据库查询：** 针对 `DetectionHistory` 表执行多个**聚合查询**。
    3. `SELECT COUNT(*), ...` `WHERE user_id = ...`
    4. `SELECT COUNT(*), ...` `WHERE user_id = ... AND created_at > (NOW() - 7 days)`
    5. `SELECT model_id, COUNT(*) ...` `GROUP BY model_id` (用于环形图)。
  - **新表：** 无需新表，但需在 `DetectionHistory` 表上为 `user_id` 和 `created_at` 建立索引以优化性能。

- 🧠 关键挑战/顾问建议：

  性能！ 随着 DetectionHistory 表增长到数百万行，这个仪表盘的 API 会变得很慢。解决方案： 必须使用缓存（例如 Redis），将用户的仪表盘统计数据缓存 10 分钟。



#### 2. ⚖️ 检测对比工具 (Comparison Tool)



- 🎯 核心价值：

  回答用户的终极问题：“哪个模型更好？”或“两次检测有什么不同？”。这为您的模型管理（MLModels）功能提供了直观的价值证明。

- **🎨 页面设计与 UX 流程 ( `/compare` )：**

  1. **入口：** 在 `/history` 页面，增加一个复选框列，用户勾选 2 个或多个任务后，出现一个 `[ 对比 (Compare) ]` 按钮。
  2. **布局：** 页面分为左右（或多列）并排对比。
  3. **视图 1：图像并排**
     - `[ 结果图 A ]` vs `[ 结果图 B ]`。
     - *高级功能：* 提供一个“同步平移/缩放”的开关，当用户缩放 A 时，B 也同步缩放。
  4. **视图 2：统计数据并排**
     - `[ 模型A: YOLOv8-n ]` vs `[ 模型B: YOLOv5-s ]`
     - `[ 检测耗时: 0.2s ]` vs `[ 检测耗时: 0.4s ]`
     - `[ 检测总数: 5 ]` vs `[ 检测总数: 3 ]`
  5. **视图 3：差异分析 (Diff Analysis) (核心！)**
     - `模型 A 独有 (A 找到 B 未找到):` `[ 1 x 海星 (0.85) ]`
     - `模型 B 独有 (B 找到 A 未找到):` `[ ]` (无)
     - `共同检测 (置信度差异):` `[ 潜水员 (A: 0.95 vs B: 0.88) ]`

- **⚙️ 后端架构与 API：**

  - **新 API：** `GET /api/v1/history/compare?ids=[id1,id2,id3]`
  - **后端逻辑：**
    1. API 接收一个 ID 列表。
    2. 从数据库中批量获取这些 `DetectionHistory` 记录及其 `result_json`。
    3. **大部分逻辑在前端：** 差异分析（Diff）的核心计算（比较两个 JSON 数组）应该在前端 JavaScript 中完成，以减轻后端压力。

- 🧠 关键挑战/顾问建议：

  “差异分析”的算法是关键。你需要定义如何判断两个检测框是“同一个物体”（例如使用 IOU - 交并比阈值）。前端的 UX 必须极其清晰，否则并排的 JSON 数据毫无意义。

### 层次二：数据驱动与行动（让数据产生价值）





#### 3. 🔔 智能告警系统 (Alerting System)



- 🎯 核心价值：

  将系统从“被动查询工具”转变为“主动安全哨兵”。用户不再需要 24 小时刷新，系统会主动为他们工作。这是巨大的价值飞跃。

- **🎨 页面设计与 UX 流程 ( `/account/alerts` )：**

  1. **布局：** 类似“邮件过滤器”的管理界面。一个 `[+ 创建新告警 ]` 按钮。
  2. **告警列表：** 显示已创建的告警，例如 `[ 规则名称: "发现高危目标" ]` `[ 状态: 激活 ]` `[ 操作: 编辑/删除 ]`。
  3. **创建/编辑告警 (模态框)：**
     - `规则名称:` (输入框)
     - `触发数据源:` (下拉框: `[所有任务]` or `[仅数据集: XX海域]` (关联功能5))
     - **`IF (触发条件):`** (一个动态规则构建器)
       - `当 [目标类别]` `[包含]` `[Shark, Diver, Wreckage]` (多选)
       - `AND` `[目标数量]` `[大于]` `[0]`
       - `AND` `[置信度]` `[大于]` `[80%]`
     - **`THEN (执行动作):`**
       - `[ ✓ ]` `发送电子邮件通知到 [user@email.com]`
       - `[ ]` `(未来) 发送 Webhook 到 [http://...]`
       - `[ ]` `(未来) 发送通知到 钉钉/飞书`

- **⚙️ 后端架构与 API：**

  - **新数据库表：** `AlertRules (id, user_id, name, conditions_json, action_json, is_active)`。
  - **API：** `POST /api/v1/alerts` (创建规则), `PUT /api/v1/alerts/{id}` (更新), `GET /api/v1/alerts` (列表)。
  - **核心逻辑 (修改 Celery 任务)：**
    1. 在 `video_tasks.py` (或图片检测服务) **完成检测后**，**不得**立即返回。
    2. 增加一个新步骤：`check_and_trigger_alerts(history_id, result_json)`。
    3. **`check_and_trigger_alerts` (新函数):**
       - 获取 `user_id`。
       - `SELECT * FROM AlertRules WHERE user_id = ... AND is_active = True`。
       - 循环遍历用户的**所有规则**。
       - **规则引擎：** 针对 `result_json` 和 `conditions_json` 执行匹配逻辑。
       - 如果匹配成功，执行 `action_json` 中的动作（例如：发送一个异步的邮件任务）。

- 🧠 关键挑战/顾问建议：

  “规则引擎”是核心。conditions_json 的解析必须高效且无懈可击。建议从非常简单的“类别包含”开始，不要过早引入复杂的 AND/OR 逻辑。



#### 4. 📊 自动化报告引擎 (Reporting Engine)



- 🎯 核心价值：

  将零散的“检测历史”打包成可交付、可分享、对管理层友好的“分析报告”。这使您的系统成为一个“决策支持系统”。

- **🎨 页面设计与 UX 流程 ( `/reports` )：**

  1. **布局：** 报告列表页。`[+ 生成新报告 ]` 按钮。
  2. **报告列表：** `[报告名称]` `[创建时间]` `[状态: ✓ 已生成]` `[操作: 下载PDF / 查看网页版]`。
  3. **生成报告 (模态框)：**
     - `报告名称:` (输入框: "11月水下安全巡检报告")
     - `时间范围:` (日期选择器: `[... to ...]` )
     - `数据源:` (下拉框: `[所有数据]` or `[数据集: XX海域]`)
  4. **交互：** 点击“生成”后，API 立即返回，页面显示报告状态为 `[ 正在生成... ]` (前端轮询)。
  5. **报告内容 (网页版或 PDF)：**
     - 封面：标题、生成日期、时间范围。
     - 统计概览：总检测数、各类别占比（饼图）、每日检测趋势（折线图）。
     - 高危目标详情：自动挑选出检测到“Shark”或“Wreckage”的关键帧图像和时间戳。
     - 附录：原始数据摘要。

- **⚙️ 后端架构与 API：**

  - **新数据库表：** `Reports (id, user_id, name, status, parameters_json, file_path_pdf, file_path_html)`。
  - **新 API：** `POST /api/v1/reports`
  - **核心逻辑 (重型 Celery 任务)：**
    1. API 接收请求，在 `Reports` 表中创建 `status='pending'` 的记录，并启动 Celery 任务：`generate_report_task.delay(report_id)`。
    2. **`generate_report_task` (Celery Worker):**
       - 更新 `status='generating'`。
       - 根据 `report_id` 获取参数（时间范围等）。
       - **执行大量的聚合查询**（比仪表盘多得多）。
       - 使用 `matplotlib` 或 `plotly.js` (在后端) 生成图表并保存为图片。
       - 使用 `Jinja2` 渲染一个 HTML 模板。
       - 使用 `WeasyPrint` (Python 库) 将此 HTML 转换为 PDF。
       - 保存文件，更新 `Reports` 表 `status='completed'` 和 `file_path_pdf`。

- 🧠 关键挑战/顾问建议：

  这是非常消耗资源的任务。必须在专用的 Celery 队列 (Queue) 上运行，以避免阻塞“视频检测”等高优任务。PDF 的排版和渲染非常繁琐。



#### 5. 🗃️ 数据集管理 (Dataset Management)



- 🎯 核心价值：

  将系统的工作单元从“单个文件”升级到“项目/数据集”。这更符合科研和工程的实际工作流。

- **🎨 页面设计与 UX 流程 ( `/datasets` )：**

  1. **布局：** 类似 Google Drive，显示“数据集”的卡片或列表。`[+ 创建新数据集 ]`。
  2. **数据集卡片：** `[名称: XX海域扫描]` `[文件数: 45]` `[创建日期]`。
  3. **数据集详情页 ( `/datasets/{id}` )：**
     - **顶部操作：** `[+ 上传文件到此数据集 ]` `[ 🚀 批量检测 (Run Batch Detection) ]`。
     - **文件列表：** 显示此数据集中所有的图片和视频文件。
  4. **批量检测 (模态框)：**
     - `选择模型:` (下拉框: `[YOLOv8-n]`)
     - `任务名称:` ("V8n 批量处理")
     - `[ 开始批量处理 (45 个文件) ]`
  5. **批量任务跟踪：** (新页面 `/batch_jobs`) 显示批量任务的总体进度（例如 `[ 30 / 45 文件处理完毕 ]`）。

- **⚙️ 后端架构与 API：**

  - **新数据库表：**
    - `Datasets (id, user_id, name, description)`
    - `DataFiles (id, dataset_id, file_path, file_type, ...)` (存储源文件)
    - `BatchJobs (id, user_id, dataset_id, model_id, status, total_tasks)`
  - **新 API：** `POST /api/v1/datasets`, `POST /api/v1/datasets/{id}/files` (上传), `POST /api/v1/datasets/{id}/run_batch`
  - **核心逻辑 (Celery Group)：**
    1. `run_batch` API 被调用后，创建一个 `BatchJob` 记录。
    2. 遍历 `DataFiles`，为**每一个**文件创建一个 Celery `process_video_task` 任务。
    3. 使用 **Celery Group（任务组）** 将这些任务捆绑在一起。
    4. `DetectionHistory` 表需要一个（可为空的）`datafile_id` 和 `batch_job_id` 外键，以便进行关联。

- 🧠 关键挑战/顾问建议：

  任务的编排和跟踪是难点。Celery Group 可以跟踪一组任务的完成情况，你需要将 group_id 存储在 BatchJob 表中，以便前端轮询总体进度。

### 层次三：“闭环”——从工具到平台





#### 6. ✍️ 在线标注与修正 (Annotation Tool)



- 🎯 核心价值：

  AI 系统的“闭环”开始。 您开始收集“真值数据 (Ground Truth)”——即用户修正过的、100% 准确的数据。这是训练更强模型的“养料”。

- **🎨 页面设计与 UX 流程 ( `/annotate/{history_id}` )：**

  1. **入口：** 在 `/history` 列表的每一行，增加一个 `[ 修正标注 ]` 按钮。
  2. **布局：** 一个全屏的、类似 `labelImg` 的标注工具界面。
  3. **UX 流程：**
     - 页面加载时，**自动加载**原始图片/视频帧。
     - **自动加载** `DetectionHistory.result_json` 中的模型检测框（显示为红色）。
     - **用户操作：**
       - **修正：** 拖动或缩放红色的框，使其变为绿色（“已确认”）。
       - **删除：** 删除模型误报的框（False Positive）。
       - **新增：** 手动绘制新的框（漏报，False Negative）。
     - **保存：** 点击 `[ 保存修正 ]` 按钮。

- **⚙️ 后端架构与 API：**

  - **新数据库表：** `Annotations (id, history_id, user_id, annotation_json, is_corrected, created_at)`
  - **新 API：** `POST /api/v1/annotations/{history_id}`
  - **核心逻辑：**
    1. `GET /api/v1/annotations/{history_id}`：
       - *优先*从 `Annotations` 表中查找“已修正”的数据。
       - 如果*没有*，则从 `DetectionHistory` 表中返回原始的 `result_json`。
    2. `POST /api/v1/annotations/{history_id}`：
       - 接收前端发来的、**完整的、修正后**的 `annotation_json`。
       - 将其存入 `Annotations` 表，并设置 `is_corrected = True`。

- 🧠 关键挑战/顾问建议：

  前端标注工具本身就是一个复杂应用。不要自己造轮子！ 寻找并集成一个成熟的开源 JavaScript 标注库（例如 label-studio-frontend 或 react-image-annotate）。



#### 7. 🚀 模型在线训练/微调 (Model Fine-Tuning)



- 🎯 核心价值：

  AI “闭环”的终点和回报。 您利用上一步收集的“真值数据”，自动训练出比以前更强的、定制化的新模型。这是平台的最终护城河。

- **🎨 页面设计与 UX 流程 ( `/admin/training` ) (管理员专属)：**

  1. **布局：** 训练任务列表。`[+ 启动新的训练任务 ]` 按钮。
  2. **任务列表：** `[任务名称]` `[基础模型]` `[状态: ✓ 已完成]` `[新模型ID: #25]`。
  3. **启动训练 (模态框)：**
     - `任务名称:` (输入框: "v1.2-海星优化模型")
     - `基础模型:` (下拉框: `[YOLOv8-n.pt]`, `[YOLOv8-s.pt]`)
     - `训练数据集:` (下拉框: `[使用所有用户修正过的数据]`)
     - `训练参数:` `Epochs: [100]` `Batch Size: [16]`
  4. **交互：** 点击“启动”后，任务进入 `[ 排队中 ]` 状态，管理员可以查看实时日志。

- **⚙️ 后端架构与 API：**

  - **新数据库表：** `TrainingJobs (id, admin_id, job_name, base_model_id, status, new_model_id, log_file_path, epochs, ...)`
  - **新 API：** `POST /api/v1/admin/training`
  - **核心逻辑 (终极重型 Celery 任务)：**
    1. API 在 `TrainingJobs` 表中创建任务，启动 `start_training_task.delay(job_id)`。
    2. **`start_training_task` (专用的 GPU Celery Worker)：**
       - 更新 `status='running'`。
       - **步骤 A (数据导出)：** `SELECT * FROM Annotations WHERE is_corrected = True`。
       - **步骤 B (数据准备)：**
         - 这是最难的脚本！
         - 它需要遍历所有 `annotation_json` 和对应的源图片。
         - 将它们转换为 YOLOv5/v8 要求的 `images/` 和 `labels/` (`.txt`) 目录结构。
         - 自动生成 `data.yaml` 配置文件。
       - **步骤 C (开始训练)：**
         - `from ultralytics import YOLO`
         - `model = YOLO(base_model_path)`
         - `model.train(data='.../data.yaml', epochs=100, ...)` (此调用会阻塞数小时)
       - **步骤 D (处理结果)：**
         - 训练完成后，`model.train()` 返回结果。
         - 找到生成的 `best.pt` 文件（在 `runs/` 目录中）。
         - 将其**复制**到您的主 `/models` 存储目录。
       - **步骤 E (更新数据库)：**
         - 在 `MLModels` 表中**创建一条新记录**，指向这个 `best.pt`。
         - 更新 `TrainingJobs` 表：`status='completed'`，`new_model_id=...`。

- 🧠 关键挑战/顾问建议：

  这是系统的“核武器”。1) GPU 资源： Celery 必须有专门的、带 GPU 的 Worker。2) 数据准备： “步骤 B”的脚本是这个功能的灵魂，极其容易出错。3) 状态与日志： 训练过程必须将 stdout (标准输出) 重定向到 log_file_path，以便管理员排错。4) 隔离： 此任务必须与“视频检测”任务严格隔离在不同的队列 (Queue) 中。
